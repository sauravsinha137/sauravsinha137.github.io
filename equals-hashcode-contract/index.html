Equals and HashCode Contract

5 Apr 2026 · 6 min read

Status: Taught on 2026-04-05

Concept Summary

The equals/hashCode contract defines the rules these two methods must follow for hash-based collections (HashMap, HashSet) to work correctly. FAANG interviewers test whether you understand the rules, can implement both correctly, know what breaks when you get it wrong, and can spot bugs in existing implementations.

The Contract — Three Rules

Rule 1: Equal objects MUST have the same hashCode

If a.equals(b) is true → a.hashCode() MUST equal b.hashCode()

Why: HashMap uses hashCode to find the bucket, then equals to find the key. If equal objects have different hashCodes, they land in different buckets. get() looks in the wrong bucket and returns null — even though the key exists.

Rule 2: Same hashCode does NOT mean equal

If a.hashCode() == b.hashCode() → a.equals(b) can be true OR false

This is just a hash collision. Two different keys in the same bucket. HashMap walks the chain and uses equals() to distinguish them. Normal and expected.

Rule 3: Unequal objects CAN have any hashCode

Different hashCodes for different objects = ideal (fewer collisions). Same hashCode for all objects = legal but terrible performance (everything in one bucket → O(n)).

The equals() Five Properties

1. Reflexive: a.equals(a) must be true

An object must equal itself.

2. Symmetric: if a.equals(b) then b.equals(a)

Classic violation: Employee.equals(String) returns true, but String.equals(Employee) returns false. Rule: only compare with your own type. Don't cross-type compare.

3. Transitive: if a.equals(b) and b.equals(c) then a.equals(c)

Violated when subclass adds a field. ColorPoint(1,2,"red").equals(Point(1,2)) = true, Point(1,2).equals(ColorPoint(1,2,"blue")) = true, but ColorPoint(red).equals(ColorPoint(blue)) = false. No good solution with inheritance — favor composition when adding value fields to a subclass.

4. Consistent: multiple calls return same result

As long as objects aren't modified. No randomness or time-dependence in equals.

5. x.equals(null) must return false

Never throw NPE, just return false. instanceof handles this automatically (null instanceof X = false).

Correct equals() Pattern

@Override
public boolean equals(Object o) {
    if (this == o) return true;                         // same reference, quick return
    if (!(o instanceof Employee other)) return false;   // null-safe + type check + cast
    return id == other.id && Objects.equals(name, other.name);  // compare fields
}

Key details:

  • Objects.equals(a, b) instead of a.equals(b) — handles null safely
  • instanceof not getClass() — allows subclass comparison (Liskov friendly)
  • Primitives (int, long) compared with ==
  • double/float compared with Double.compare()/Float.compare() — NOT ==
    • 0.1 + 0.2 == 0.3 is false (floating point imprecision)
    • NaN == NaN is false but Double.compare(NaN, NaN) == 0 is true
    • -0.0 == 0.0 is true but Double.compare(-0.0, 0.0) != 0

instanceof vs getClass()

  • instanceof: Manager IS an Employee → comparison works across hierarchy
  • getClass(): Manager is NOT the same class as Employee → strict match only
  • Effective Java: use instanceof for non-extendable classes. If subclasses add fields, consider composition.

Correct hashCode() Pattern

@Override
public int hashCode() {
    return Objects.hash(name, id);   // same fields as equals()
}

Golden rule: same fields in both methods.

  • Field in equals but not hashCode → equal objects might hash differently → BREAKS Rule 1
  • Field in hashCode but not equals → legal but more collisions than necessary
  • Same fields → correct AND optimal

Why 31 in hash computation: Objects.hash internally uses 31 * result + element.hashCode(). 31 is an odd prime, and 31 * x is optimized by JVM to (x << 5) - x.

Java Records — Free Implementation

public record Employee(String name, int id) {}

Automatically generates correct equals() (all fields), hashCode() (all fields), and toString(). Immutable by default — safe as HashMap keys. Mention this in interviews to show modern Java knowledge.

The Mutable Key Trap

Employee emp = new Employee("alice", 1);
Set<Employee> set = new HashSet<>();
set.add(emp);           // hashCode based on "alice" → bucket 7
emp.setName("bob");     // hashCode now based on "bob" → bucket 3
set.contains(emp);      // looks in bucket 3 → not found! But emp IS in the set (bucket 7)

Object is in the set but unreachable. Can't find it, can't remove it, can't garbage collect it (set holds reference). Memory leak.

Rule: Never mutate fields used in hashCode after inserting into a hash collection. Use immutable fields or records.

String vs StringBuilder Behavior

String — overrides equals() and hashCode(). Two String objects with same characters are equal.

Set<String> set = new HashSet<>();
set.add(new String("hello"));
set.contains(new String("hello"));  // → true

StringBuilder — does NOT override equals()/hashCode(). Uses Object defaults (memory address).

Set<StringBuilder> set = new HashSet<>();
set.add(new StringBuilder("hello"));
set.contains(new StringBuilder("hello"));  // → false (different objects)

Why: StringBuilder is mutable. If hashCode was content-based, it would change on every append() → objects get lost in hash collections. JDK intentionally uses default identity-based equals/hashCode.

Safe as HashMap keys: String, Integer, Long, Double (all wrappers) — override both methods, immutable. Dangerous as keys: StringBuilder, ArrayList, arrays — don't override or are mutable.

Equality Fields Don't Have to Be All Fields

Example: Two books are equal if they have the same ISBN + edition. Title is not part of equality.

public class Book {
    private String isbn;
    private String title;
    private int edition;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Book b)) return false;
        return edition == b.edition && Objects.equals(isbn, b.isbn);
        // title deliberately excluded
    }

    @Override
    public int hashCode() {
        return Objects.hash(isbn, edition);
        // title deliberately excluded — matches equals
    }
}

Common Interview Questions

  1. What happens if you override equals() but not hashCode()? (Different hashCodes for equal objects → wrong bucket → get() returns null)
  2. Write correct equals() and hashCode() for a given class.
  3. Can two unequal objects have the same hashCode? (Yes — collision, legal and expected)
  4. Why use the same fields in both methods?
  5. instanceof vs getClass() in equals — trade-offs?
  6. How do Java records handle equals/hashCode?
  7. What are the five properties of equals()?
  8. Why is StringBuilder unsafe as a HashMap key?
  9. What's wrong with comparing doubles using == in equals()?
  10. What is the mutable key trap?

Gotchas

  • Overriding equals() without hashCode() is the #1 collections bug in Java.
  • name.equals(other.name) throws NPE if name is null. Use Objects.equals().
  • price == other.price for doubles is wrong. Use Double.compare().
  • Mutable fields in hashCode → object gets "lost" in HashMap after mutation.
  • Symmetric violation with cross-type equals (Employee.equals(String)).
  • Transitivity violation when subclass adds fields to equals — no clean solution with inheritance.
  • StringBuilder, ArrayList, arrays don't override equals/hashCode — unsafe as hash keys.
