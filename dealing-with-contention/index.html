Dealing with Contention

2 Oct 2026 · 13 min read

0. The one sentence

Every contended resource has exactly one source of truth. Make the contended thing a single addressable cell (row / key / item), then pick the cheapest tool that closes the read→write gap.

Everything below is a variation of compare-and-set: "write this, but only if the thing is still what I think it is." You already know this from AtomicInteger.compareAndSet() in Java. The database versions are the same idea at a different layer.

1. The problem: lost update

Read-modify-write with a gap in the middle:

Alice: SELECT seats → 1      Bob: SELECT seats → 1
Alice: 1 > 0, charge card    Bob: 1 > 0, charge card
Alice: UPDATE seats = 0
                             Bob: UPDATE seats = -1   ← lost update, double sale

The read and the write are two statements. The world changes between them. Microseconds in memory, milliseconds over a network, and that's enough.

Interview framing: "This is a read-modify-write race. The fix is always to make the write conditional on what I read, or to hold the thing still while I decide." Say this sentence before you pick a tool.

2. The escalation ladder (take the first rung that fits)

Rung Shape of the decision Tool Cost
1 "if" about the row I'm writing Conditional write (WHERE predicate) lowest
2 read → decide in app code → write; collisions rare Optimistic concurrency (version column) retry on conflict
3 read → decide in app code → write; collisions common Pessimistic lock (SELECT ... FOR UPDATE) everyone pays lock cost
4 invariant spans rows that never collide (write skew) SERIALIZABLE isolation, or materialize onto one row abort/retry, tracking overhead
5 exclusivity must outlive one transaction (a wait, an external call) Distributed lock / lease (Redis SET NX PX, DB columns, ZK/etcd) new infra or extra row contention

The article orders 2 and 3 as pessimistic-then-optimistic. For interviews the decision rule is the same either way: how often do writers actually collide? Rare → optimistic. Common → pessimistic.

3. Rung 1: Conditional writes (SQL spells CAS as WHERE)

UPDATE concerts
SET available_seats = available_seats - 1
WHERE concert_id = 'weeknd_tour' AND available_seats > 0;

Safe under concurrency with no explicit lock. The DB serializes updates to the same row. Bob's statement waits for Alice's, then re-evaluates available_seats > 0 against her result, matches 0 rows.

Gotcha 1: 0 rows updated is NOT an error

The statement succeeds silently. If the next statement is an unconditional INSERT INTO tickets, Bob gets a ticket for a seat he never got. Either check the affected-row count in app code and roll back, or chain the insert off the update:

WITH reservation AS (
  UPDATE concerts SET available_seats = available_seats - 1
  WHERE concert_id = 'weeknd_tour' AND available_seats > 0
  RETURNING concert_id
)
INSERT INTO tickets (user_id, concert_id, seat_number, purchase_time)
SELECT 'user123', concert_id, 'A15', NOW() FROM reservation;

In Java/JPA: int rows = em.createQuery(...).executeUpdate(); if (rows == 0) throw new SoldOutException(); inside the @Transactional method so the exception rolls everything back.

Gotcha 2: guard the thing people actually fight over

A counter guard answers "is a seat left". It cannot answer "is this seat left". With 20 seats left, two buyers both decrement successfully and both insert seat A15. The count is correct and the seat is double-sold.

Fix: one row per seat, CAS on the seat row:

UPDATE tickets SET status = 'sold', user_id = 'user123'
WHERE concert_id = 'weeknd_tour' AND seat_number = 'A15' AND status = 'available';

The seat count becomes derived data (or a cached counter decremented in the same transaction).

Bar-raiser line: "The database can only protect a conflict it can see. My first job is to make the contended thing exist as a single row."

Same move, other stores

DynamoDB ConditionExpression, Redis SET NX, Cassandra lightweight transaction (IF), HTTP If-Match, Java AtomicReference.compareAndSet, ConcurrentHashMap.putIfAbsent.

4. Rung 3: Pessimistic locking (SELECT ... FOR UPDATE)

When the decision can't be a WHERE predicate. Example: group of 4 wants adjacent seats. App must read the seat map, find a contiguous block, then claim it. Two groups read the same map, both choose A15–A18, second writer clobbers.

BEGIN;
SELECT seat_number FROM seats
WHERE concert_id = 'weeknd_tour' AND section = 'floor' AND status = 'available'
FOR UPDATE;                      -- locks every returned row until COMMIT
-- app picks A15-A18
UPDATE seats SET status = 'sold', user_id = 'user123'
WHERE concert_id = 'weeknd_tour' AND seat_number IN ('A15','A16','A17','A18');
COMMIT;

Second group's SELECT FOR UPDATE blocks until commit, then sees A15–A18 gone.

Java: JPA em.find(Seat.class, id, LockModeType.PESSIMISTIC_WRITE) or Spring Data @Lock(LockModeType.PESSIMISTIC_WRITE) on a repository method. Must be inside a transaction or the lock is released immediately.

Failure modes interviewers probe

  1. Locking too much, too long. Table lock = serialize all writers. Lock held across a payment API call = every buyer waits on Stripe's p99. Rule: no I/O inside the lock. Do external calls before acquiring or after releasing.
  2. Deadlock from inconsistent ordering. See §8. Fix: sort lock targets by a deterministic key before acquiring.
  3. Everyone pays. Even the 99% of transactions that never collide pay lock overhead. That's the argument for optimistic when contention is low.

5. Rung 2: Optimistic concurrency control (OCC)

Assume conflicts are rare. Don't block. Detect at write time and retry.

Needs a value on the row that changes on every write. Read it, then write with WHERE version = <what I read>.

-- Both read: seats=1, version=42
UPDATE concerts SET available_seats = available_seats - 1, version = version + 1
WHERE concert_id = 'weeknd_tour' AND version = 42;
-- Alice: 1 row. Bob: 0 rows → re-read + retry, or tell user "sold out".

Same gotcha as rung 1: 0 rows is silent. Check the count.

Java: JPA @Version private long version; does this automatically. A stale write throws OptimisticLockException (Spring wraps as ObjectOptimisticLockingFailureException). Catch and retry with bounded attempts + jitter. Spring Retry @Retryable(OptimisticLockException.class, maxAttempts = 3) is the idiomatic shape.

What can be the "version"?

Candidate OK? Why
Dedicated int counter, +1 every write ✅ default changes on every write, no ABA
updated_at timestamp ⚠️ only if every write touches it and clock resolution is fine enough
Business value that moves one way (auction high bid) ✅ monotonic, so no ABA
Business value that can round-trip (balance, review_count) ❌ ABA problem, see §8
Postgres xmin system column ✅ built-in row version

Pessimistic vs optimistic: the decision

"How often do writers actually collide?" Collisions common → lock up front, retries cost more than the lock. Collisions rare (most e-commerce) → optimistic, eat the occasional retry. Under hot contention OCC degrades badly: retry storms, wasted work.

6. Rung 4: Write skew and isolation levels

All three tools above protect rows both transactions touch. Write skew is when they don't.

On-call example: rule = at least one engineer on call. Alice and Bob both on call. Both step down at once. Alice reads "Bob is on" → removes herself. Bob reads "Alice is on" → removes himself. Each writes its own row. Both commit. Nobody on call. No shared row, so no WHERE, no FOR UPDATE, no version catches it. The conflict is in what each read to decide.

Isolation levels (options, not a ladder)

Level Sees Default in
READ UNCOMMITTED dirty reads rarely used
READ COMMITTED only committed data, each statement a fresh snapshot PostgreSQL
REPEATABLE READ snapshot fixed for the whole transaction MySQL/InnoDB
SERIALIZABLE result equals some serial order; DB tracks read-write dependencies nobody by default

Only SERIALIZABLE catches write skew. REPEATABLE READ does not. Under SERIALIZABLE one of Alice/Bob aborts with a serialization error, app retries, retry sees the new state and backs off.

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call WHERE team_id = 'payments' AND is_active = true;  -- 2
UPDATE on_call SET is_active = false WHERE engineer_id = 'alice';
COMMIT;  -- may abort with serialization_failure → retry

Java: @Transactional(isolation = Isolation.SERIALIZABLE); catch CannotSerializeTransactionException and retry.

Cost and the cheaper alternative

SERIALIZABLE tracks every read/write, aborts throw away work. Most NoSQL stores don't offer it at all. So the preferred move is to materialize the invariant onto one row: a team.on_call_count column you decrement with WHERE on_call_count > 1, or SELECT ... FOR UPDATE on the team row before anyone steps down. That turns cross-row skew back into same-row contention that rung 1 or 3 handles cheaply. Same lesson as "one row per seat."

7. Rung 5: Distributed locks (leases)

Every tool above lives inside one DB transaction. A DB lock dies with its transaction. Sometimes exclusivity has to span a wait or an external call: Ticketmaster holds seat A15 for 10 minutes while you type card details. FOR UPDATE can't do that (pins a connection for 10 min, invisible to other app servers).

Fix: stop holding the lock as a transaction, hold it as data: who holds it, and when the hold expires. Any server can read it. It outlives any transaction.

Where the lease lives How Pro Con
Redis SET seat:A15 user123 NX PX 600000 fast, TTL = automatic cleanup, any server sees it not airtight: holder stalls past TTL (GC pause) → two holders briefly. Fine for soft holds, not for money. Redis itself is a SPOF
DB columns UPDATE seats SET reserved_by=?, reserved_until=NOW()+10min WHERE seat_id=? AND (reserved_until IS NULL OR reserved_until < NOW()) no new infra, same consistency as your data, expiry in the WHERE = no cleanup job slower than cache, lock row becomes a hot spot
ZooKeeper / etcd ephemeral node / lease via ZAB / Raft survives partitions and leader failure, auto-release on client session death you run a consensus cluster

NX is non-negotiable. Without it a second SET overwrites the first holder's lock.

Release safely: store a unique token as the value, and release with a Lua script "DEL only if value == my token". Otherwise a slow holder whose TTL expired can delete someone else's lock. Redisson RLock does this for you (plus a watchdog that extends TTL while the holder is alive).

UX win, not just correctness: the hold shrinks the fight window from "entire checkout" to "the instant of selection". Nobody fills out payment then gets "seat gone".

Cross-ref: design-uber § Deep Dive 3 uses exactly this for driver offers: SET driver_lock:8842 ride:xyz NX PX 10000.

8. Common deep dives (be ready to whiteboard each)

"How do you prevent deadlocks with pessimistic locking?"

Transfer A→B and B→A simultaneously. T1 locks Alice then wants Bob. T2 locks Bob then wants Alice. Cycle.

Ordered locking: sort all participants by a global key (primary key) before acquiring. Transfer between 456 and 123 always locks 123 first, regardless of who initiated. "Lock the initiator first" is wrong, it's not globally consistent.

Even with ordering, handle deadlock as a retryable error. Every major DB runs deadlock detection by default and kills one victim. Catch (DeadlockLoserDataAccessException in Spring), retry with locks taken in order. Lock-wait timeout is a different, coarser backstop for "someone held a lock too long", not a cycle.

Same as Java's lock-ordering rule from java/02-concurrency: synchronized(min(a,b)) { synchronized(max(a,b)) {...} }.

"What is the ABA problem with OCC?"

Reuse review_count as the version. Read 100. A review is deleted (99), a new one lands (100). Your WHERE review_count = 100 passes and clobbers the intervening update. Equality can't see the round trip.

Fix: dedicated monotonic version column, incremented on every write even if no business field changed. Fallback without a column: put every field you read into the WHERE. Or use Postgres xmin. (Java analogue: AtomicStampedReference.)

"Everyone wants the same row. Now what?"

Hot key / celebrity problem. Sharding doesn't help (one row). Load balancing doesn't help (servers queue on the same row). Read replicas don't help (the fight is over writes).

  1. Change the problem first. 10 identical items → 10 separate auctions. Likes/follows → eventually consistent, nobody notices a 2-second lag on a follower count.
  2. Queue-based serialization. All writes for that key go to one partition of a queue, consumed by a single worker. Contention becomes sequencing. Queue absorbs the spike. Trade-off: throughput capped at one worker, and that worker is a SPOF you back with a standby. Partition key = the contended resource so ordering holds.

"Why not just use a distributed lock for everything?"

Because it adds a component, a network hop, and a new failure mode (TTL expiry under GC pause, Redis outage) to solve something a WHERE clause already solves. Interviewers mark this down. Default to the single DB. Escalate only when the hold must span a wait/external call.

9. Scope boundary (say this out loud)

Everything here assumes one authoritative store for the contended resource. Two cases leave this pattern entirely:

  • One operation must atomically span multiple shards/services (transfer between accounts on different shards) → distributed transaction / saga / outbox. Different pattern.
  • Same record writable in multiple places (multi-leader / leaderless replication) → conflict resolution: LWW, vector clocks, CRDTs. Replication topic, see 07-cap-theorem-consistency.

Nine times out of ten you can keep it in one DB. Do that.

10. Interview recognition signals and canned openers

Recognize: limited inventory (tickets, flash sale, auction), double-booking (meeting rooms, drivers, seats), balance updates, "what if two users do X at the same time". Flag it yourself during NFRs under "strong consistency". Don't wait to be asked.

Problem Tool Opener
Auction OCC with high bid as version (monotonic, no ABA) "Bidders contend on one item, bids only go up, so I'll CAS on the current high bid."
Ticketmaster Reservation lease (10-min TTL) + CAS on seat row at purchase "The real win is the hold at selection time, so nobody pays and then loses the seat."
Flash sale OCC with version column on inventory + cart hold with TTL "Inventory is a hot row, I'll consider queue serialization if contention is extreme."
Uber dispatch Driver status lease, Redis SET NX PX 10000 "One driver, one outstanding offer, expiry owned by the store not my process."
Yelp rating update OCC with dedicated version column (review_count has ABA)
Banking within one DB Pessimistic with ordered locking, or OCC "Cross-shard transfers leave this pattern and become a distributed transaction."

Don't overcomplicate: admin-only edits → OCC + retry. Single-user data → no coordination. Read-heavy → OCC.

11. One-liner arsenal

  • "A lost update is a read-modify-write with a gap. Every fix either makes the write conditional or holds the row still."
  • "WHERE is how SQL spells compare-and-set."
  • "Zero rows updated is a success, not an error. Check the count or chain the insert."
  • "The guard must sit on the thing people are fighting over. A counter can't tell two buyers of A15 apart."
  • "Pessimistic when collisions are common, optimistic when rare. The question is collision rate."
  • "Write skew has no shared row. Only SERIALIZABLE sees it, or I materialize the invariant onto one row."
  • "A DB lock dies with its transaction. A lease is a lock held as data."
  • "Redis NX without a fencing token is a soft lock. Fine for seat holds, not for money."
  • "Hot key: change the problem first, then serialize through one queue partition."
  • "Cross-shard atomicity isn't contention, it's a distributed transaction."
