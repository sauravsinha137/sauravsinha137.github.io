HLD Problem: Design URL Shortener (Bit.ly)

20 Oct 2026 · 13 min read

Designing Bit.ly: The "Easy" Question That Isn't

A long-form writeup of the URL shortener problem, inspired by the Hello Interview breakdown, with my own diagrams, numbers, Java notes, and commentary layered on top. Diagrams are in Mermaid.

URL shortener is the problem interviewers reach for when they want to see how you think, not what you know. There are almost no hard components. What is hard is being disciplined: scoping fast, noticing the one number that shapes everything (reads outnumber writes ~1000:1), and then picking the simplest thing at every fork while still being able to say why the fancier option exists.

Three tensions drive the whole design:

  1. Uniqueness vs. shortness vs. speed of code generation. You can have any two cheaply; all three takes a decision.
  2. Read-heavy to an absurd degree. 100M DAU clicking, ~1 write/sec creating. The write path can be boring; the read path has to be fast and always up.
  3. Availability over consistency. A redirect that is 50ms stale is fine. A redirect that 500s is not.

1. Scoping the Problem

Functional requirements (the top 3)

  1. Submit a long URL, get a short one back
    • optional custom alias (short.ly/my-launch)
    • optional expiration date
  2. Visit the short URL, get redirected to the original

Deliberately below the line: auth/accounts, click analytics, spam & malware filtering. Say so out loud. Analytics in particular is the trap: it is "obviously" part of Bit.ly, and it drags in an entire event pipeline. Park it and reclaim the time for the deep dives.

Non-functional requirements — where the design is decided

NFR What it forces
Uniqueness: one short code → exactly one long URL The code generation strategy is the first deep dive
Redirect latency < 100ms Cache in front of the DB; possibly CDN/edge
Availability ≫ consistency, 99.99% Replicas, cache as a shield, fail-open on the read path
1B URLs, 100M DAU Sizing says a single Postgres fits; scale the services, not the data

The number to say early: read:write ≈ 1000:1. Every later decision (cache, service split, DB choice) is downstream of it. Interviewers listen for whether you derive the architecture from this ratio or just recite "add a cache".

2. Core Entities and Data Model

Keep it to a list at first; flesh out columns once the API is settled.

erDiagram
    USER ||--o{ URL : creates
    URL {
        string short_code PK
        string original_url
        timestamp created_at
        timestamp expires_at
        uuid created_by FK
    }
    USER {
        uuid user_id PK
    }

One table does the job. short_code is the primary key (it is the lookup key, so it gets the index for free). Row size estimate: code ~8B, URL ~100B, two timestamps ~16B, alias ~100B, padding/metadata → call it 500B to be safe.

Dedup or not? Hashing the URL would let the same long URL always map to the same code. Most real shorteners don't dedup: two users want separate expirations, separate analytics, separate aliases. Say the tradeoff, pick no-dedup, move on.

3. API Surface

POST /urls
{ "long_url": "https://example.com/a/very/long/path",
  "custom_alias": "optional",
  "expiration_date": "optional ISO-8601" }
→ 201 { "short_url": "https://short.ly/abc123" }

GET /{short_code}
→ 302 Found
   Location: https://example.com/a/very/long/path
→ 404 if unknown · 410 Gone if expired

301 vs 302 — a guaranteed follow-up

301 Moved Permanently 302 Found
Browser caches it Yes — later clicks skip your server entirely No — every click hits you
Server load Lower Higher
Can you expire / edit the link later? Not for users who already clicked Yes
Analytics possible? No (you never see repeat clicks) Yes

Pick 302. The whole product value of a shortener (control, expiration, click counting) depends on owning every hop. If the interviewer pushes "but 301 saves load" the answer is: the cache makes the load trivial, and the control is the product.

4. High-Level Architecture

flowchart LR
    C[Client] -->|POST /urls| S[Primary Server]
    C -->|GET /abc123| S
    S --> DB[(Postgres<br/>urls table)]
    S -.->|302 Location| C

Write path: validate URL format → canonicalize → generate a short code (magic box for now) → if a custom alias was supplied, use that instead after checking it is free → INSERT → return.

Read path: look up code → if missing, 404 → if expires_at < now(), 410 → else 302 with Location.

Expired rows: a nightly sweeper job deletes them, or just leave them and let the read path reject. What actually matters is that the cache TTL ≤ time-to-expiry, so a stale entry cannot outlive its row.

That is a working system. Everything below is the interviewer asking "and how do you make it good?"

5. Deep Dive 1 — Generating Unique Short Codes

Three constraints: unique, short, cheap to produce. Walk the ladder.

❌ Prefix of the long URL

www.linkedin.com/in/... → short.ly/www.link. Every LinkedIn profile collides. Mentioned only to show the uniqueness constraint is real.

🟡 Hash and truncate

canonical = canonicalize(long_url)      # lowercase host, strip default port, trailing slash…
digest    = sha256(canonical)
code      = base62(digest)[:8]           # 62^8 ≈ 218 trillion codes

Why base62? a-z A-Z 0-9 — base64 minus + and /, because / is a path separator and + decodes as a space in query strings.

The collision math (say this unprompted): with |S| possible codes and n already used, the chance the next one collides is n / |S|. At 1B URLs and 8-char codes that is 1B / 218T ≈ 5×10⁻⁶ per insert — rare, not zero. So you must have a UNIQUE constraint on short_code, catch the violation, and retry with a salt, bounded to 3–5 attempts. Every retry is an extra DB round trip on the write path.

Truncating a hash is also a choice between determinism (same URL → same code, which gives you dedup) and unpredictability (add an HMAC secret). Know which one you are picking.

✅ Global counter + base62

id   = INCR counter           # Redis, atomic, single-threaded
code = base62(id)
  • Zero collisions by construction. No retry loop, no uniqueness check before insert.
  • Short: 1,000,000,000 in base62 is 15ftgG — six characters at a billion URLs. 62⁶ ≈ 56B before you need a 7th character; 62⁷ ≈ 3.5T.
  • Reversible: base62⁻¹(code) gives you the row id if you ever shard by id.

Two costs, both of which the interviewer will raise:

  1. Predictability. 15ftgG → 15ftgH is the next link. Anyone can enumerate every URL you have ever shortened. Mitigation: a cheap reversible bijection before encoding (XOR with a secret, or a Feistel round / multiplicative inverse mod 62ⁿ). Or accept it: short links are public by design. State the choice.
  2. Coordination. A counter is a single point of agreement. Fine with one server; a problem with many. That is Deep Dive 3.

Custom aliases vs. generated codes. They share one namespace, so a user could claim 15ftgH today and break tomorrow's generated code. Fix: give generated codes a prefix character aliases are not allowed to use, or keep aliases in a separate column/namespace and check both on read.

Java note: the encode is a 10-line loop (id % 62, id /= 62, reverse). Writing Base62.encode(long) on the whiteboard, with the alphabet as a static final char[], is a cheap credibility win.

6. Deep Dive 2 — Making Redirects Fast

A DB lookup on an indexed primary key is already O(log n). The question is really about the 100ms budget and 100M DAU pounding one table.

✅ In-memory cache in front of the DB

flowchart LR
    C[Client] -->|GET /abc123| S[Read Service]
    S -->|1. GET abc123| R[(Redis<br/>code → url)]
    R -.->|hit| S
    S -->|2. miss: SELECT| DB[(Postgres)]
    S -.->|SET abc123 url EX ttl| R
    S -.->|302| C

Cache-aside, read-through on miss. Orders of magnitude to have ready:

Tier Access time Ops/sec
Memory ~100 ns millions
SSD ~0.1 ms ~100k IOPS
HDD ~10 ms ~100–200

What to say about it, beyond "add Redis":

  • Eviction: LRU. Click traffic is Zipfian; a small hot set serves most reads.
  • TTL ≤ expiry so an expired link never redirects from cache.
  • Invalidation is nearly free here because mappings are immutable. The only writes that touch the cache are deletes/expirations: DEL the key.
  • Cold start / warm-up: after a cache restart the DB takes the full read load briefly. Replicas absorb it; so does a cache with persistence.
  • Negative caching: cache 404s for a short TTL, or an attacker enumerating random codes turns every miss into a DB hit.

✅✅ CDN / edge redirect (the "if money is no object" tier)

Serve short.ly through a CDN and run the redirect in an edge function (Cloudflare Workers, Lambda@Edge). Popular codes resolve at the PoP nearest the user and never reach your origin. Trade: cross-PoP invalidation, edge runtime limits, cost, and harder debugging. Offer it, name the trade, don't build it unless the interviewer wants it.

7. Deep Dive 3 — Scaling to 1B URLs and 100M DAU

Storage: do the arithmetic, then relax

500 B × 1B rows = 500 GB. One modern SSD. Writes are ~100k/day ≈ 1 row/sec. So: a single Postgres primary with read replicas is correct, and anyone proposing sharding at this point has not done the math. Say that explicitly; it is a senior signal.

DB choice: anything (Postgres, MySQL, DynamoDB). The cache has already taken the read load off it and the write rate is trivial. Pick the one you can defend — Postgres.

If the primary dies: streaming replicas + automatic failover for availability; periodic snapshots for durability. Because reads come from the cache and replicas, a primary failover mostly degrades writes, which is the path nobody is waiting on.

Compute: split read and write, scale them separately

flowchart LR
    C[Client] --> GW[API Gateway / LB]
    GW -->|GET /code| RS[Read Service ×N]
    GW -->|POST /urls| WS[Write Service ×M]
    RS --> R[(Redis cache)]
    RS --> DB[(Postgres<br/>primary + replicas)]
    WS -->|INCR counter 1000| CTR[(Redis counter)]
    WS --> DB
    WS -.->|DEL on delete/expire| R

    style R fill:#1a4d2e,color:#fff
    style CTR fill:#1a4d2e,color:#fff
    style RS fill:#2d2d4d,color:#fff

Reads are stateless lookups; they scale horizontally for free. Writes are the only place with shared state, so they deserve the attention.

The counter under horizontal scale

Many Write Service instances must agree on "next id". Options:

  • Central Redis INCR. Single-threaded, atomic, 100k+ ops/sec, which is five orders of magnitude more than our write rate. One extra network hop per create; negligible.
  • Counter batching. Each instance does INCRBY counter 1000 once and hands out ids from its local range. Redis traffic drops by 1000×. A crashed instance leaks the unused tail of its range; who cares, we need unique, not contiguous.
  • Redis failover. Sentinel/Cluster for HA. If a failover loses a few un-replicated increments you could, in theory, hand out an id twice. The UNIQUE constraint on short_code is the backstop: the second insert fails and you fetch a new batch. (Same conditional-write-at-the-datastore principle as the first rung in 14-dealing-with-contention.)
  • Multi-region. Give each region a disjoint range (A: 0–1B, B: 1B–2B). Writes stay local; reads are served from regional caches. No cross-region coordination on the hot path.

Alternative the interviewer may want you to name: Twitter Snowflake-style ids (timestamp + machine id + sequence) remove the central counter entirely, at the cost of 11-char codes. For a shortener, the shortness wins and the Redis counter stays.

8. The Assembled System

flowchart TB
    C[Client] --> GW[API Gateway]
    GW -->|GET| RS[Read Service<br/>cache → DB → 302]
    GW -->|POST| WS[Write Service<br/>counter → base62 → INSERT]
    WS --> CTR[(Redis counter<br/>batched INCRBY)]
    RS --> CACHE[(Redis cache<br/>code → url, LRU, TTL ≤ expiry)]
    RS --> DB
    WS --> DB[(Postgres<br/>urls: short_code PK UNIQUE,<br/>original_url, expires_at, created_by)]
    CACHE -.->|optional| CDN[CDN / edge redirect]

    style CACHE fill:#1a4d2e,color:#fff
    style CTR fill:#1a4d2e,color:#fff

The theme, in one sentence: the read:write asymmetry licensed every simplification. A single primary DB is fine because writes are 1/sec. A cache is enough because the hot set is small and immutable. A single Redis counter is fine because 100k ops/sec vs 1/sec is not a contest. The design is simple because the numbers say it can be, and being able to show that arithmetic is the whole interview.

9. Interview Questions They Will Actually Ask

  1. Why 302 and not 301? Control: expiration, edits, analytics. 301 lets the browser bypass you forever.
  2. How do you guarantee uniqueness? Counter + base62 (no collisions) or hash + truncate + UNIQUE + bounded retry. Know both, choose the counter, explain the predictability trade.
  3. How long are the codes? 6 chars covers 56B (62⁶). 7 chars covers 3.5T. 1B URLs → 15ftgG.
  4. Why base62 not base64? / and + are not URL-safe.
  5. Custom alias collides with a generated code? Prefix/namespace separation, or check both on insert.
  6. What if two users submit the same long URL? Two codes, by default. Dedup is a product decision, not a correctness one.
  7. What if Redis (counter) goes down? Batching means writes continue until local ranges drain. Failover via Sentinel. Lost increments are fine; UNIQUE catches any double-issue.
  8. What if the cache goes down? DB + replicas serve reads, slower. Availability over latency. Never fail the redirect because the cache is gone.
  9. Expired links? 410 Gone. Cache TTL ≤ expiry; optional sweeper job.
  10. How do you stop enumeration of all links? Secret bijection on the id before encoding, or accept public-by-design. Rate-limit the read path (see design-rate-limiter) so scanning is expensive.
  11. Traffic 10×? Reads: more Read Service instances and a bigger cache, then CDN. Writes: still 10/sec. Nothing structural changes, and saying so confidently is the point.
  12. Add analytics without slowing redirects. Emit a click event to Kafka after sending the 302; a consumer aggregates. Never put analytics on the synchronous path.
