Load Balancing & Reverse Proxies

19 Apr 2026 · 7 min read

1. What problem are we solving?

Four drivers, in order of importance at FAANG scale:

  1. Horizontal scaling — fan traffic across many servers.
  2. High availability — one server dies, reroute.
  3. Geographic distribution — serve from closest POP.
  4. Offload — TLS, compression, auth, rate limiting at edge.

Interviewer test: articulate which driver applies before invoking an LB.

2. Reverse Proxy vs Load Balancer

Term Meaning
Forward proxy Sits in front of clients (corporate egress). Wrong direction here.
Reverse proxy Sits in front of servers. Does LB + caching + SSL + auth + compression + WAF.
Load balancer Specifically distributes traffic. Subset of reverse-proxy capabilities.

Classic trap: "Is NGINX a LB or reverse proxy?" → Reverse proxy that can load balance.

3. Layer 4 vs Layer 7 — most-asked question

L4 (TCP/UDP):

  • Routes on (src IP, src port, dst IP, dst port). No payload parsing.
  • Pros: fast, protocol-agnostic, supports TLS passthrough.
  • Cons: no URL/header/cookie routing.
  • Examples: AWS NLB, HAProxy mode tcp.

L7 (HTTP/gRPC):

  • Parses HTTP. Routes on path, host, header, cookie, method.
  • Pros: smart routing, host-based routing, request inspection/modification, HTTP/2 multiplexing.
  • Cons: slower (parsing), must decrypt TLS to inspect.
  • Examples: AWS ALB, NGINX (HTTP), Envoy, HAProxy mode http.

Rule: L7 for HTTP apps. L4 for TLS passthrough, non-HTTP protocols, raw throughput.

4. Algorithms

Algorithm When
Round robin Stateless, homogeneous servers, uniform request cost
Weighted RR Heterogeneous hardware
Least connections Long-lived connections or heterogeneous request duration
Least response time Mixed backend performance
IP hash Poor-man's sticky
Consistent hashing Sharded state (caches, stateful partitions) — NOT stateless tiers
Power of two choices Modern LBs (Envoy, HAProxy) — near-optimal with low overhead

Key trap: consistent hashing for stateless app servers is wrong.

  • Its only benefit is minimal remapping on topology change — only matters when a key has an owning node.
  • Stateless servers have no owners. Any server works.
  • Consistent hashing distributes load worse than RR (statistical hotspots), is blind to actual load, and adds complexity for zero benefit.
  • "Local cache locality" = not stateless. Fix: externalize cache (Redis/Memcached, which uses consistent hashing internally), app tier becomes truly stateless, use RR/least-conn.

5. Health checks

  • Active: LB polls /health. M consecutive failures → unhealthy.
  • Passive: observe real traffic; 5xx/timeout → unhealthy.
  • Use both.

Deep-healthcheck trap: checking every dependency cascades failures. FAANG pattern: separate /live (process alive) and /ready (deps OK). Kubernetes formalized this.

Connection draining / graceful shutdown: on scale-down or deploy, stop new requests to node, let existing finish until grace timeout (30–60s). Essential for long-lived connections (WebSocket, gRPC streams, file uploads).

6. Sticky sessions

Needed when server stores session state in memory. Methods: cookie-based, IP hash.

Problems: uneven load, server death loses session, breaks elasticity.

FAANG-preferred: externalize session state to Redis; app tier stateless. Sticky only when truly unavoidable (WebSocket pin, legacy).

7. SSL/TLS termination

  1. At LB (most common): LB decrypts, sees plaintext, L7 routing. Backend gets plain HTTP (internal) or re-encrypted.
  2. Passthrough (TLS bridging): LB forwards ciphertext (L4 only). Needed for end-to-end encryption, client cert auth, strict compliance.
  3. Re-encrypt: terminate at LB → new TLS to backend. More CPU, better security posture.

Why terminate at LB: central cert mgmt, offload crypto CPU, enables L7.

8. Global load balancing

  • GeoDNS: authoritative DNS returns different IP per resolver location. Coarse (resolver ≠ client), slow failover (DNS TTL). Tools: Route 53, Cloudflare DNS.
  • Anycast: same IP announced from multiple PoPs via BGP; internet routes packets to topologically nearest. Sub-second failover, DDoS-resistant. Examples: 8.8.8.8, 1.1.1.1, CDN edge IPs.
  • Client-side LB: client picks endpoint from a list (gRPC default, service mesh).

Big players combine: GeoDNS picks region → anycast within region handles PoP selection and failover.

9. HA of the LB itself

  • Active-passive: VRRP + floating IP (keepalived).
  • Active-active: DNS RR or ECMP.
  • Cloud-managed: ALB/NLB multi-AZ by default.

10. Real-world tools

  • NGINX — reverse proxy/L7 standard.
  • HAProxy — best L4 + solid L7, battle-tested.
  • Envoy — modern, xDS dynamic config, service mesh native (Istio), gRPC-native.
  • AWS: NLB (L4), ALB (L7 HTTP/gRPC), CloudFront (global CDN).

11. gRPC + L7 — critical for microservices interviews

gRPC uses one long-lived HTTP/2 connection per client, multiplexing many RPCs as streams.

Why L4 fails: L4 balances per-connection. All RPCs from one client pin to one backend → hotspots. 3 clients + 10 backends = 3 backends used.

Why L7 works: HTTP/2-aware L7 routes per-stream across backends.

"HTTP/2-aware" vs "gRPC-native":

  • HTTP/2-aware: ALB, NGINX. Routes streams, understands HTTP semantics.
  • gRPC-native: Envoy, Linkerd. Understands gRPC status codes (separate from HTTP status), deadlines, streaming RPCs, per-method routing/retry.

Picks:

  • K8s → Envoy (Istio/Linkerd)
  • AWS → ALB (not NLB)
  • On-prem → Envoy or NGINX w/ gRPC module

K8s gotcha: vanilla ClusterIP Service = L4 (iptables/IPVS) → gRPC hotspots. Fix: service mesh (Envoy sidecar) or headless Service + client-side LB (round_robin policy in channel).

12. Interview gotchas

  1. Consistent hashing for stateless tier — wrong.
  2. Sticky sessions as primary solution — bar raiser pushes back; externalize state.
  3. RR with heterogeneous request cost — least-connections instead.
  4. "L7 is always better" — wrong; L4 wins for TLS passthrough, non-HTTP, raw throughput.
  5. Forgetting connection draining during scale-down/deploy.
  6. Forgetting the LB needs its own HA.
  7. Not separating /live and /ready.
  8. L4 LB for gRPC — creates connection-pinning hotspots.

Networking primer (Tier 1 only)

PoP (Point of Presence): a small edge datacenter near users (Cloudflare ~300, Google ~200). Hosts caches, LBs, TLS terminators. Backs to origin (core DC) for cache misses.

BGP (Border Gateway Protocol): how ASes (Autonomous Systems) tell each other which IPs they can reach. Enables anycast: announce same IP from many locations, each external router picks nearest.

DNS:

  • Authoritative DNS = owner of domain's records.
  • Recursive resolver = client's helper that walks hierarchy and caches answers.
  • GeoDNS uses resolver IP (or client subnet via ECS) to return location-appropriate IP.

Deeper networking (AS-path selection, peering vs transit, ECMP, VRRP) = overkill for generalist FAANG HLD. Skip.

Interview-grade one-liner arsenal

"For a global user base, I'd put a CDN in front. GeoDNS points each user to their nearest edge PoP, which serves cached content. Cache miss → edge fetches from origin over backbone. Anycast handles sub-second PoP failover."

"Sticky sessions are a smell; I'd externalize session state to Redis so any server can serve any user. Keep app tier stateless → free horizontal scale."

"For gRPC I need an L7 HTTP/2-aware LB like Envoy or ALB, not L4 — otherwise all RPCs from one client pin to one backend."

"Consistent hashing belongs on the cache tier where keys have owners. On a stateless tier it hurts more than it helps — I'd use least-connections."
