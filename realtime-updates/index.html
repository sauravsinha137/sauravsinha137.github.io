Real-time Updates

29 Jul 2026 · 8 min read

1. What problem are we solving?

Delivering updates from server to client the moment they happen — chat messages, live locations, doc edits. Standard HTTP is request-response: client asks, server answers, connection closes. Real-time needs the server to push proactively.

The two-hop framing (use this structure in interviews):

  1. Hop 1 (client ↔ server): how does the update reach the client? → protocol choice (polling / long-polling / SSE / WebSocket / WebRTC)
  2. Hop 2 (source → server): how does the update reach the right server holding the client's connection? → trigger choice (pull-polling / consistent hashing / pub-sub)

Most candidates only talk about hop 1. Covering hop 2 is what separates senior answers.

2. Networking foundations (just enough)

  • Layer 3 (IP): packet routing, best-effort — packets can be lost, duplicated, reordered.
  • Layer 4 (TCP/UDP): TCP = connection-oriented, ordered, reliable, costs setup (3-way handshake: SYN → SYN-ACK → ACK) and per-connection state. UDP = connectionless, spray and pray.
  • Layer 7 (HTTP, WebSocket, WebRTC): application protocols on top of TCP.

Two interview-relevant consequences:

  1. Every round trip adds latency — connection setup happens before your data moves.
  2. A TCP connection is state on both ends. Without keep-alive, you pay setup/teardown per request.

L4 vs L7 load balancers (comes up constantly with WebSockets)

L4 L7
Operates on TCP/IP (IPs, ports) HTTP content (URL, headers, cookies)
Connection Persistent client↔server TCP passthrough Terminates connection, opens new one to backend
Speed Fast, minimal inspection More CPU (inspects packets)
Best for WebSockets / persistent connections HTTP traffic, long-polling, content-based routing

Rule of thumb: L4 for WebSockets (same TCP connection sticks to one server natively); L7 for HTTP-based approaches (more routing flexibility).

3. Hop 1: Client-server protocols

Simple polling — the baseline

Client hits /api/updates every N seconds.

  • ✅ Dead simple, stateless, no special infra, quick to explain in interview.
  • ❌ Latency up to poll interval; wasted requests; connection churn (mitigate with HTTP keep-alive longer than the poll interval).
  • Use when: latency of 2–5s is acceptable. Many "real-time" problems don't actually need real-time. Propose it explicitly: "I'll start with polling so I can focus on X; we can upgrade later."

Long polling — the easy upgrade

Client makes request → server holds it open until data exists → responds → client immediately re-requests.

  • ✅ Near real-time, plain HTTP, stateless, works everywhere.
  • ❌ Latency for rapid-fire updates: after each response the client must make a new round trip. Two updates 10ms apart: first arrives in ~100ms, second up to ~290ms (finish first response + new request + response). Also: HTTP overhead per message, hanging requests complicate monitoring, browser per-domain connection limits.
  • Infra note: every hop (load balancer, proxy) must tolerate long-lived requests — don't let the LB hang up at 30s when your server holds for 60s. Typical hold: 15–30s.
  • Use when: infrequent updates, e.g. waiting for a payment/async job to complete.

Server-Sent Events (SSE) — efficient one-way street

An HTTP response with Transfer-Encoding: chunked that never "finishes" — server streams chunks as events occur. Browser-native via EventSource.

  • ✅ One persistent connection, no per-message re-request (fixes long-polling's rapid-update latency), auto-reconnect built into browsers, still plain HTTP.
  • ✅ Reconnection gap-fill: SSE standard has Last-Event-ID — client reconnects with the last ID it saw, server replays what was missed.
  • ❌ One-way only (server → client). Some proxies/LBs buffer responses and silently break streaming — nasty to debug. Browser per-domain connection limits.
  • Use when: server-push-only. Live dashboards, notification feeds, AI token streaming (ChatGPT-style) — the canonical modern example.

WebSockets — full-duplex champion

Starts as HTTP, then Upgrade handshake switches the TCP connection to the WebSocket protocol (cookies/auth headers from the HTTP phase carry over). Both sides then send opaque messages freely.

  • ✅ True bi-directional, lowest overhead per message (no headers), ideal for high-frequency read+write.
  • ❌ Stateful connections → hard parts:
    • Load balancing: prefer L4; use "least connections" strategy; you're stuck with each allocation decision.
    • Deployments: restarting servers severs connections → need reconnect logic + catch-up on missed messages.
    • Every infra hop must support the upgrade.
  • Reference architecture: terminate WebSockets in a dedicated, rarely-redeployed WebSocket service at the edge; keep the rest of the system stateless and let it scale independently.
  • Use when: high-frequency AND bi-directional (chat, multiplayer games, collaborative editing).
  • ⚠️ Common candidate mistake: reaching for WebSockets too eagerly. Pattern that often wins: SSE for updates + plain HTTP POST for writes. Writes are usually infrequent enough.

WebRTC — peer-to-peer

Browsers talk directly to each other; server is only a lightweight signaling server (peer discovery + connection info exchange — itself needs WebSocket/SSE!). NAT traversal via STUN (hole punching to get publicly routable address) and TURN (relay fallback when direct fails).

  • ✅ Lowest latency, offloads bandwidth from your servers, native audio/video.
  • ❌ Most complex; connection setup delay; NAT/firewall pain.
  • Use when: audio/video calls (only real choice), or offloading server load in collaborative apps (cursor/presence sharing — Canva; Google-Docs-style editing with CRDTs).

Decision flowchart (memorize)

  1. Not latency-sensitive? → Simple polling
  2. Server-push only, no frequent client writes? → SSE
  3. High-frequency bi-directional? → WebSocket
  4. Audio/video? → WebRTC

4. Hop 2: Getting updates to the right server

With persistent connections (long-poll/SSE/WS), one specific server holds User C's connection. When a message for User C arrives anywhere in the system, how does it find that server?

Option A: Pull via polling

No routing needed — updates land in a DB, clients poll it (messages WHERE ts > last_seen). Source and consumer fully decoupled.

  • ❌ Latency; and watch the math: 1M clients polling every 10s = 100k reads/sec.
  • Use when: paired with simple polling, real-time not truly needed.

Option B: Push via consistent hashing

Each user is owned by one server, determined by hashing.

  • Naive: server = hash(userId) % N, with N and server list managed in a coordination service (ZooKeeper/etcd). Client connects anywhere → gets redirected to its owner. Sender hashes recipient's ID → knows exactly which server to deliver to.
  • Problem: changing N remaps almost everyone → consistent hashing: servers + users on a hash ring, user connects to next server clockwise. Scaling moves only the affected ring segment.
  • ✅ Predictable routing, minimal churn on scale events, keeps heavy per-connection state in exactly one place.
  • ❌ Complex; needs coordination service; server failure loses that connection state.
  • Scaling event choreography (senior talking point): record old+new assignments → drain/reconnect clients gradually → dual-deliver to old+new server during transition → finalize.
  • Use when: connections carry expensive server-side state (e.g. Google Docs: loaded doc + pending ops + collaborator sync).

Option C: Push via Pub/Sub (default choice)

Central pub/sub layer (Redis pub/sub, Kafka) holds the routing state. Client connects to any lightweight endpoint server, which subscribes to that user's topic. Publishers push to the topic; pub/sub fans out to subscribed endpoint servers; they forward down the existing connections.

  • ✅ Endpoint servers stateless-ish and interchangeable → trivial LB ("least connections"); efficient broadcast to many clients; state confined to pub/sub layer. Latency cost minimal (<10ms).
  • ❌ Pub/sub is a SPOF/bottleneck (scale with Redis Cluster — shard subscriptions by key); no visibility into subscriber connect/disconnect; many-to-many connections between pub/sub nodes and endpoint servers.
  • Use when: small messages, no heavy per-connection state, broadcast-heavy. The default for most interview problems.

Rule: heavy per-connection state → consistent hashing; lightweight message forwarding → pub/sub.

5. Common deep dives (prepare answers)

"How do you handle connection failures / reconnection?"

  • Heartbeats (ping/pong) to detect zombie connections — a broken WebSocket doesn't always signal.
  • Track delivery: sequence numbers or per-user message queue; on reconnect, client sends last-seen ID and server replays the gap. Redis Streams is a popular implementation. (SSE gives you Last-Event-ID for free.)

"Celebrity posts, millions of followers need the update?"

  • Naive fan-out to millions of per-user feeds crushes the system. Cache the update once + hierarchical distribution: regional/intermediate servers pull once, push to their local clients. Batching + aggregation layers.

"Message ordering across distributed servers?"

  • Full generality: vector clocks / logical timestamps. But for product-style interviews the right answer is usually: funnel related messages through a single server/partition (e.g. one Kafka partition per chat room) → single point stamps a total order. Trades some scalability for simplicity — say that trade-off out loud.

6. Interview strategy

  • Name the requirement early: "messages need instant delivery to all participants — WebSockets" / "character-level edits need sub-second propagation."
  • Don't over-engineer. If polling suffices, propose it with the upgrade path as a backdoor. Simplicity is valued at senior+.
  • Cover both hops. Protocol choice AND server-side propagation.
  • Canonical mappings:
    • Chat/WhatsApp → WebSocket + pub/sub, ordering per room, presence/typing indicators
    • Live comments (FB Live) → SSE/WS + hierarchical aggregation for extreme fan-out
    • Google Docs → WebSocket + consistent hashing (doc state) + OT/CRDT for conflicts
    • Live dashboards / Robinhood → SSE, discuss "how real-time is real-time enough"
    • ChatGPT → SSE token streaming
    • Games/calls → WebRTC (+ WS for server coordination)

7. Quick-fire gotchas

  • Long polling ≠ low latency for bursts of updates (the re-request round trip).
  • SSE breaks silently behind buffering proxies.
  • WebSocket upgrade must be supported by every hop, not just your server.
  • L7 LB terminates connections — doesn't guarantee same backend TCP connection; L4 does.
  • Browser per-domain connection limits bite both long-polling and SSE.
  • Deployments churn persistent connections — always have a reconnect + catch-up story.
  • WebRTC still needs a server (signaling + STUN/TURN); "peer-to-peer" isn't serverless.
  • 1M pollers × 10s interval = 100k TPS — always do the polling math.
