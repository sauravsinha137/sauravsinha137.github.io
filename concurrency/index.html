Java Concurrency

5 Apr 2026 · 8 min read

Status: Taught on 2026-04-05

Concept Summary

Java concurrency covers thread lifecycle, synchronization mechanisms, the Java Memory Model (JMM), executor framework, and concurrent utilities. You must be able to write thread-safe code and explain WHY it's safe.

Chapter 1: Threads

Creating Threads

  • Extend Thread: class MyThread extends Thread — limits you to single inheritance
  • Implement Runnable (preferred): new Thread(() -> ...) — separates task from mechanism
  • Callable: Like Runnable but returns a result and can throw checked exceptions. Used with ExecutorService.

start() vs run()

  • t.start() — creates a NEW OS thread, then calls run() on it
  • t.run() — just a normal method call on the CURRENT thread. No new thread.
  • start() can only be called once. Second call throws IllegalThreadStateException.

Thread States

NEW → RUNNABLE → TERMINATED
         ↕
    BLOCKED (waiting for synchronized lock)
    WAITING (wait(), join(), park())
    TIMED_WAITING (sleep(), wait(timeout), join(timeout))

Chapter 2: The Shared Memory Problem

Two Fundamental Problems

Visibility: Thread A writes, Thread B doesn't see it (CPU cache isolation). Atomicity: Multi-step operation interrupted halfway (read-modify-write race).

count++ is THREE operations: READ → ADD → WRITE. Two threads interleaving → lost updates.

Every concurrency tool solves one or both of these.

Chapter 3: synchronized

Acquires the object's intrinsic monitor lock. Solves BOTH visibility and atomicity.

Three Forms

  1. Synchronized block: synchronized (lockObject) { } — most flexible, you choose the lock
  2. Synchronized instance method: public synchronized void m() — locks on this
  3. Synchronized static method: public static synchronized void m() — locks on MyClass.class

Critical: Instance method locks this, static method locks MyClass.class. They are DIFFERENT locks. One does NOT block the other.

Reentrancy

Same thread can acquire the same lock multiple times. Without this, a synchronized method calling another synchronized method on the same object would deadlock.

What It Guarantees

  • Atomicity: One thread at a time inside the block
  • Visibility: On exit, writes flush to main memory. On entry, reads come from main memory. (Happens-before relationship)

Locking on this Can Be Too Broad

If an object has 5 synchronized methods protecting different data, they all compete for the same lock. Use dedicated lock objects for fine-grained locking:

private final Object countLock = new Object();
private final Object nameLock = new Object();

Chapter 4: volatile

Solves visibility. Does NOT solve atomicity.

What It Guarantees

Every volatile write goes to main memory immediately. Every volatile read comes from main memory. No CPU cache staleness.

What It Does NOT Guarantee

volatile int count; count++ is NOT thread-safe. Still three operations (read, add, write) that can be interleaved.

When to Use

  • Simple flags: volatile boolean running = true
  • Publishing immutable object references: volatile Config config = loadConfig()
  • NOT for compound operations (check-then-act, read-modify-write)

Chapter 5: wait(), notify(), notifyAll()

Low-level thread communication. Used inside synchronized blocks.

Critical Rules

  1. Must be inside synchronized. wait() releases the lock. No lock held = IllegalMonitorStateException.
  2. wait() releases the lock. sleep() does NOT. Key interview question.
  3. Always while, not if, around wait(). Spurious wakeups can happen — condition might still be false after waking.
  4. Prefer notifyAll() over notify(). notify() wakes one random thread. If the wrong one wakes, nobody makes progress.

sleep() vs wait()

wait() sleep()
Releases lock? YES NO
Must be in synchronized? YES NO
Woken by notify()/notifyAll() Timeout
Purpose Thread coordination Just pausing

Chapter 6: ReentrantLock

Explicit lock with features synchronized lacks.

Advantages Over synchronized

  • tryLock() — non-blocking attempt
  • tryLock(timeout) — attempt with timeout
  • lockInterruptibly() — can be interrupted while waiting
  • ReadWriteLock — readers don't block readers
  • Multiple Condition objects (vs one wait/notify set)
  • Fairness option

Always Unlock in finally

lock.lock();
try {
    // critical section
} finally {
    lock.unlock();  // MUST unlock — otherwise lock leaks on exception
}

ReadWriteLock

  • Reader + Reader → both proceed
  • Reader + Writer → writer waits
  • Writer + Writer → one waits
  • Huge throughput gain for read-heavy workloads (90%+ reads)

When to Use Which

Default: synchronized (simpler, fewer bugs). Use ReentrantLock only when you need tryLock, timeout, interruptibility, or ReadWriteLock.

Chapter 7: Java Memory Model (JMM)

Happens-Before Rules

"A happens-before B" means everything Thread A did before point A is guaranteed visible to Thread B after point B.

  1. Program order: Within one thread, each statement happens-before the next.
  2. Monitor lock: Unlock happens-before subsequent lock of same monitor.
  3. Volatile: Volatile write happens-before subsequent volatile read of same variable. Also acts as a memory fence — ALL writes before the volatile write are visible after the volatile read.
  4. Thread start: thread.start() happens-before any action in the started thread.
  5. Thread join: All actions in a thread happen-before join() returns.
  6. Transitivity: If A→B and B→C, then A→C.

Chapter 8: Executors — Thread Pools

Why Thread Pools

Creating new Thread per task is expensive (OS thread creation). Thread pools reuse threads.

Pool Types

  • newFixedThreadPool(n) — exactly n threads, unbounded queue
  • newCachedThreadPool() — creates threads as needed, reuses idle ones
  • newSingleThreadExecutor() — one thread, sequential execution
  • newScheduledThreadPool(n) — delayed and periodic tasks

ThreadPoolExecutor Internals

Task arrives:
1. Threads < corePoolSize → create new thread
2. Threads >= corePoolSize → put in queue
3. Queue full AND threads < maxPoolSize → create new thread
4. Queue full AND threads >= maxPoolSize → rejection policy

Rejection policies: AbortPolicy (throws), CallerRunsPolicy (caller runs it), DiscardPolicy (silent drop), DiscardOldestPolicy (drop oldest, retry).

Interview trap: newFixedThreadPool uses unbounded LinkedBlockingQueue. Tasks queue forever → can OOM. Production code uses bounded queues.

Shutdown

  • shutdown() — stop accepting, finish running tasks
  • shutdownNow() — interrupt running tasks
  • Always shut down or JVM won't exit (pool threads keep it alive)

Submitting Tasks

  • execute(Runnable) — fire and forget
  • submit(Callable) — returns Future<V>, call future.get() to block for result

Chapter 9: Concurrent Utilities

AtomicInteger/Long/Reference

Lock-free thread-safe operations via CAS (compare-and-swap).

  • incrementAndGet(), getAndIncrement()
  • compareAndSet(expected, new) — atomic check-and-update
  • No lock, no blocking. CAS fails → automatic retry.

CountDownLatch — "Wait for N things to finish"

  • new CountDownLatch(3) — count starts at 3
  • Workers call countDown() — decrements count
  • Main thread calls await() — blocks until count hits 0
  • One-time use. Cannot reset.
  • Use case: "Start server after all 3 subsystems initialize"

CyclicBarrier — "Wait for each other, then go together"

  • All N threads call await() at the checkpoint
  • When all arrive, all proceed simultaneously
  • Reusable — resets automatically after each use
  • Use case: multi-phase simulation

CountDownLatch vs CyclicBarrier

CountDownLatch CyclicBarrier
Reusable? No Yes
Who waits? One thread for N All N for each other
Use case Wait for tasks Synchronize at checkpoints

Semaphore — "Only N at a time"

  • new Semaphore(3) — 3 permits
  • acquire() — take permit (blocks if none)
  • release() — return permit
  • Use case: rate-limit access (e.g., max 3 DB connections)

BlockingQueue — Thread-Safe Queue

  • put() — blocks if full (producer waits)
  • take() — blocks if empty (consumer waits)
  • Types: ArrayBlockingQueue (bounded), LinkedBlockingQueue (optionally bounded), SynchronousQueue (zero capacity, direct handoff)
  • Replaces manual wait/notify for producer-consumer
  • Poison pill pattern: send special value to signal consumers to stop. One pill per consumer.

Chapter 10: Deadlock

Two threads each hold a lock the other needs. Neither can proceed.

Four Conditions (ALL must hold)

  1. Mutual exclusion — only one thread holds the lock
  2. Hold and wait — holds one lock while waiting for another
  3. No preemption — can't force lock release
  4. Circular wait — A waits for B, B waits for A

Prevention — Break Any One Condition

  • Lock ordering: Always acquire locks in same order. No cycle possible.
  • tryLock: If can't get second lock, release first and retry. Breaks hold-and-wait.
  • Timeout: tryLock(5, SECONDS) — give up after timeout.

Gotchas

  • volatile does NOT make compound operations atomic
  • synchronized on different objects = no mutual exclusion
  • Instance and static synchronized methods use DIFFERENT locks
  • Thread.sleep() does NOT release locks. wait() DOES.
  • notify() can wake the wrong thread. Prefer notifyAll().
  • Spurious wakeups are real. Always use while-loop around wait().
  • newFixedThreadPool has unbounded queue — can OOM in production.
  • Never call thread.stop() — use flags or interruption for graceful shutdown.
  • Deadlock requires ALL four conditions. Break any one to prevent.
