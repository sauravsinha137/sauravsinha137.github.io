Concept Summary

Java Collections Framework internals — how HashMap, ConcurrentHashMap, TreeMap, ArrayList, and LinkedList actually work under the hood. FAANG interviewers expect you to explain hashing, bucket structure, collision resolution, resizing, and thread-safety mechanisms — not just API usage.

HashMap Internals

Structure

  • Backed by array of Node<K,V> (buckets). Default capacity 16, load factor 0.75.
  • Each bucket holds a linked list of nodes (or a red-black tree if chain gets long).

How put(key, value) Works

  1. Hash the key: h = key.hashCode() ^ (key.hashCode() >>> 16)
    • >>> 16: unsigned right shift — slides upper 16 bits down to lower 16, fills left with zeros
    • ^ (XOR): combines both halves so lower bits carry information from all 32 bits
    • Why: bucket index uses only lower bits (hash & (capacity-1)), so without this spreading, upper bits are wasted
  2. Find bucket: index = hash & (capacity - 1) — bitwise AND, works because capacity is power of 2
  3. Check for existing key: walk the chain, compare hash then equals(). If found, replace value.
  4. Insert: if key not found, add new node at head of chain.
  5. Resize check: if size > capacity * loadFactor, double the array and rehash everything.

Hash Function Deep Dive

  • hashCode() returns a 32-bit int. The hash doesn't know the table size.
  • Table could be 16 buckets (uses 4 bits) or 65536 buckets (uses 16 bits).
  • h ^ (h >>> 16) folds upper bits into lower bits so ALL bits contribute to bucket index.
  • Without this, keys with same lower bits but different upper bits would always collide.
  • Analogy: Aadhaar number (12 digits) assigned to room (1 digit). You want all 12 digits to influence the room assignment.

Bit Operations Reference

  • >>> (unsigned right shift): slides bits right, fills left with zeros ALWAYS. Unlike >> which fills with the sign bit (1s for negative numbers).
  • ^ (XOR): outputs 1 when bits are DIFFERENT, 0 when SAME. Unbiased — preserves info from both inputs. XOR with 0 changes nothing (identity). XOR is reversible.
  • & (AND): outputs 1 only when BOTH bits are 1. Used for bucket index because hash & (n-1) extracts the lower bits.

Treeification (Java 8+)

  • When a bucket's linked list reaches 8 nodes → converts to red-black tree (O(log n) search).
  • When it shrinks to 6 → converts back to linked list (hysteresis prevents thrashing).
  • Worst case get(): O(log n) not O(n).

Resizing

  • Triggers when size > capacity * loadFactor (default: 12 for initial capacity 16).
  • Doubles array size. Rehashes ALL entries — O(n) operation.
  • The 13th insert into a default HashMap triggers resize.
  • Capacity must be power of 2 — each resize adds one bit to the index mask.
  • Performance tip: if you know you'll have 1000 entries, initialize with new HashMap<>(1334) to avoid resizing.

Thread Safety

  • HashMap is NOT thread-safe.
  • Two threads putting simultaneously → lost updates (one node silently disappears).
  • During resize → can create chain cycles → infinite loop in get().

Null Handling

  • Permits one null key (hashes to bucket 0) and multiple null values.
  • containsKey() bug: get(key) != null fails if value is null. Must walk chain to check if node exists.

ConcurrentHashMap Internals

Why It Exists

  • Hashtable: one global lock. Thread A reads bucket 5, Thread B waits even though it wants bucket 12.
  • Collections.synchronizedMap(): same problem — wraps every method in one lock.
  • ConcurrentHashMap: one lock per bucket. Threads on different buckets never block each other.

Three Concurrency Strategies

Strategy 1: Lock-Free Reads (get())

  • get() uses NO locks at all.
  • Safe because of volatile:
    • table is volatile → threads see the latest array reference
    • Node.value is volatile → threads see the latest value
    • Node.next is volatile → threads follow the latest chain
  • Reads are always fast, never blocked.
  • Weakly consistent: may briefly see stale data during concurrent write, but sees it once the write completes.
  • get() should retry if table was swapped during read (our implementation). Real CHM uses ForwardingNode instead.

Strategy 2: Per-Bucket Locking for Writes (put())

  • Lock ONLY the target bucket. Other buckets remain free.
  • With 16 buckets, up to 16 threads can write simultaneously.
  • Stale check after acquiring lock: if (tab != table) continue — if resize swapped the table, retry.
  • Size increment and resize trigger happen OUTSIDE the bucket lock to avoid deadlock.

Strategy 3: Resize

  • Lock ALL buckets (in order, to prevent deadlock between resize threads).
  • Create NEW nodes in new table — don't move old ones. Old chains must stay intact for lock-free get().
  • Swap table with volatile write. Waiting put() threads wake up, see stale check fail, retry on new table.
  • Only one thread resizes at a time (tryLock() — skip if someone else is already resizing).
  • Real CHM uses cooperative resizing: all threads help transfer, ForwardingNode marks transferred buckets.

Why No Null Keys/Values

  • get() returning null is ambiguous: key doesn't exist OR value is null?
  • In HashMap you resolve with containsKey() — safe because single-threaded.
  • In ConcurrentHashMap, another thread can modify the map between get() and containsKey(). Two calls are NOT atomic.
  • Banning null makes API unambiguous: null from get() = key definitely doesn't exist.

AtomicReferenceArray vs volatile Array

  • volatile Node[] table: only the REFERENCE is volatile, not individual elements. table[5] = x is NOT a volatile write.
  • AtomicReferenceArray: each element independently has volatile read/write semantics.
  • Analogy: volatile notice board means you see if the board is replaced. But if someone changes a sticky note on it, no guarantee you see the change.

Atomic Compound Operations

  • Individual get() and put() are atomic. But get-then-put is NOT atomic (check-then-act race).
  • Fix: use replace(key, oldVal, newVal), compute(), merge(), putIfAbsent() — these do check+update inside the bucket lock.

TreeMap

  • Red-black tree. O(log n) for get/put/remove.
  • Keys must be Comparable or provide Comparator.
  • NavigableMap methods: floorKey(), ceilingKey(), subMap().
  • Does NOT allow null keys (throws NPE). Allows null values.
  • Use when you need sorted iteration or range queries. Otherwise prefer HashMap.

ArrayList vs LinkedList

  • ArrayList: dynamic array, O(1) random access, O(n) insert/delete in middle, amortized O(1) append.
  • LinkedList: doubly-linked, O(1) insert/delete at known position, O(n) random access. Implements Deque.
  • ArrayList almost always wins due to CPU cache locality (contiguous memory).
  • LinkedList only for queue/deque usage, and even then ArrayDeque is usually better.

Common Interview Questions

  1. How does HashMap handle collisions? When does it treeify?
  2. What happens when you put a key with same hashCode but different equals?
  3. Why is ConcurrentHashMap's size() approximate?
  4. What's the time complexity of HashMap.get() in worst case? (O(log n) after treeification)
  5. Why doesn't ConcurrentHashMap allow null keys/values?
  6. How does HashMap resize? What's the performance implication?
  7. When would you choose TreeMap over HashMap?
  8. What happens if you modify a key object after putting it in a HashMap?
  9. What's the difference between volatile Node[] and AtomicReferenceArray?
  10. Why does ConcurrentHashMap use per-bucket locking instead of a global lock?
  11. Is get() followed by put() thread-safe on ConcurrentHashMap? How to fix it?

Gotchas

  • Modifying a key's hashCode-relevant fields after insertion → entry unretrievable.
  • HashMap iteration order is NOT guaranteed (use LinkedHashMap for insertion order).
  • Collections.synchronizedMap() ≠ ConcurrentHashMap — coarse-grained vs fine-grained locking.
  • hashCode() returning a constant → HashMap degrades to O(n).
  • volatile on array reference does NOT make elements volatile.
  • ConcurrentHashMap's get() is lock-free but weakly consistent.
  • check-then-act on ConcurrentHashMap is a race condition — use compound operations.
