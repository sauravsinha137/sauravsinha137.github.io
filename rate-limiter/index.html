LLD Problem: Rate Limiter

20 Jun 2026 · 3 min read

Baseline architecture (locked 2026-06-20)

  • Single axis of variation = the algorithm. Unify it behind one interface:
    interface RateLimitAlgorithm { boolean allow(String key); }
    Caller never knows which concrete algorithm is active → runtime-swappable (Strategy).
  • key = WHO is limited (userId / ip / apiKey). The algorithm holds per-key state; it does not know what the key means.
  • Config is injected at construction, NOT passed per call. allow(key) stays clean.
  • TimeSource abstraction injected so refill/window logic is testable by fast-forwarding a fake clock instead of Thread.sleep. Production wires System::currentTimeMillis.
  • Scope: single-machine / in-memory for LLD. Hide state behind a Store seam so Redis is a localized swap later — say this out loud, then park distributed (that's HLD).

Key misconception corrected

NOT all algorithms share (limit, window) config. Each algorithm owns its own config shape:

Algorithm What it does Config
Fixed window x requests per fixed window (resets on boundary) limit, windowSec
Sliding window log store each request timestamp, count last window limit, windowSec
Sliding window counter weighted blend of current + previous window limit, windowSec
Token bucket bucket of tokens, refills at rate; allows bursts capacity (burst), refillRate
Leaky bucket queue drained at constant rate; smooths output queueCapacity, leakRate

Construction seam (build when algorithm #2 arrives, not on n=1)

Different constructors per algorithm is CORRECT, not a smell. Absorb the difference in two places:

  • Per-algorithm config as records under a sealed interface AlgorithmConfig.
  • An AlgorithmFactory with an exhaustive switch over the sealed configs (compile-time safety in Java 21). The caller/RateLimiter only ever see RateLimitAlgorithm. Construction differences are quarantined in the factory.

Two axes not to conflate

  • Rule selection: path / route → Rule{ algorithm, config } (e.g. /login 5/min, /search 100/min).
  • Key: the identity counted within that rule.

allow vs throttle

A rate limiter's job is allow or reject. "Throttle" (delay/queue a request) is a separate component, not smuggled into allow().

Token Bucket — implemented (TDD, all green)

Files: the project source TimeSource, TokenBucket, TokenBucketTest}.java(No JUnit in project → ran with plainjavac/java` 21 via a tiny assert harness.)

Design decisions worth defending in the room:

  • Per-key state: ConcurrentHashMap<String, Bucket>, bucket created lazily via computeIfAbsent (atomic creation).
  • Fractional tokens (double): so sub-second refill accrues (rate 2/s, 500ms elapsed → 1 token). Integer tokens would lose this.
  • Lazy refill: no background thread. On each call compute tokens = min(capacity, tokens + elapsed * refillPerMilli). O(1), no scheduler.
  • Start full: a fresh client gets its full burst immediately.
  • Thread-safety: synchronized on the per-Bucket tryConsume() (refill + consume is a read-modify-write). Lock granularity is per key, so no global contention. A volatile/plain field would lose updates under races → over-admission.
  • Concurrency proven: 200 racing threads on one key, capacity 100 → exactly 100 admitted.

Open items / next

  • Bucket eviction — unbounded keys = memory leak. Need idle TTL / LRU / size cap. (Interviewers WILL ask.)
  • Return type — boolean now; production wants Decision{ allowed, retryAfterMs, remaining } for 429 Retry-After.
  • Algorithm #2 = FixedWindow → forces the sealed AlgorithmConfig + AlgorithmFactory seam.
  • Then sliding-window-counter (the "fix fixed-window's boundary burst" story).
